# 003 データベース：PostgreSQL と Prisma

## 決めたこと

データベースは PostgreSQL を使い、プログラムからは Prisma を通して操作する。

## 比べた候補

| 候補 | このアプリで使うとどうなるか |
| --- | --- |
| DynamoDB（AWSの、表を使わないデータベース） | AWSと相性がよい。ただし、「食品 → 目安量 → 読み取った項目」のような、表どうしのつながりを扱うのが苦手 |
| SQLite（ファイル1つのデータベース） | 準備がとても簡単。ただし、公開して何人もが同時に使うのには向かない |
| MySQL | PostgreSQL と同じく、表どうしのつながりを扱える。このアプリの使い方なら、大きな差はない |
| **PostgreSQL（選んだもの）** | 表どうしのつながりを扱える。AWS の RDS でも使える |

| 候補 | プログラムから操作するとどうなるか |
| --- | --- |
| SQLを直接書く | 自由に書けるが、表の形と TypeScript の型を、自分でそろえ続ける必要がある |
| **Prisma（選んだもの）** | 表の形を1つのファイル（schema.prisma）に書くと、TypeScript の型が自動で作られる。表の変更も、記録（マイグレーション）として残せる |

## 選んだ理由

- ER図のとおり、食品・目安量・読み取った項目などの表がつながっているので、表どうしのつながりを扱えるデータベースが合っている
- Prisma を使うと、表の形から TypeScript の型が自動で作られる。001で TypeScript を選んだ理由（データの形のまちがいを、動かす前に見つける）を、データベースまで広げられる
- 表の変更が記録に残るので、あとから「いつ、なぜ表を変えたか」を説明できる

## あきらめたこと（トレードオフ）

- データベースのサーバーを用意する必要がある。SQLite より準備に手間がかかり、公開するときの費用にも気をつける必要がある
- MySQL との差は小さい。Prisma の情報が多いことと、AWS で使えることから PostgreSQL にした
